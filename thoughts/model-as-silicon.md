# 当模型成为芯片：Taalas HC1、ROMA 与 TOM

> **日期**：2026-09-08  
> **主题**：模型专用推理芯片、ROM 固化权重、算法—硬件协同设计  
> **一句话判断**：这条路线不会终结 GPU，但可能把一部分稳定、高频、低延迟的推理负载，从“运行在计算机上的软件”变成“计算机本身”。

---

## 1. 问题不是算不动，而是搬不动

LLM 的自回归解码通常一次只生成一个 token。以 batch=1 为例，每生成一个 token，模型都要遍历一遍权重。一个 8B 模型即使量化到 4 bit，权重仍约为：

```text
8 × 10^9 parameters × 4 bits ÷ 8 ≈ 4 GB
```

如果这些权重每次都从外部存储读取，那么 200 tokens/s 已经需要约 800 GB/s 的有效权重带宽；17,000 tokens/s 对应的朴素带宽需求更达到 68 TB/s。实际系统会通过缓存、并行和批处理改善利用率，但对单用户、低延迟解码来说，权重搬运仍是主要约束。

GPU 的答案是更快的 HBM、更大的缓存和更高的并行度。Taalas、ROMA 与 TOM 采用了另一种思路：

> 不再反复把权重搬到计算单元，而是让权重长期驻留在计算附近，甚至成为硅片物理结构的一部分。

这不是简单地“给芯片加一块 ROM”，而是重新划分模型、存储和计算之间的边界。

## 2. Taalas HC1 做了什么

Taalas 将这条路线称为 **Hardcore Model**，口号是“The Model is The Computer”。首个技术演示产品 HC1 面向 Llama 3.1 8B，公开参数包括：

- TSMC 6nm 工艺；
- 815 mm² die；
- 530 亿晶体管；
- 2.5 kW 服务器配置；
- Llama 3.1 8B 在 1K 输入、1K 输出条件下达到约 17,000 tokens/s/user。

它最重要的变化不是某个矩阵乘单元，而是取消了“模型权重是运行时从 HBM 加载的数据”这一前提。权重与计算被放到同一芯片中，外部显存、先进封装和大规模权重搬运的重要性随之下降。

但目前需要把事实与宣传明确分开：

1. 17K tokens/s 是 Taalas Labs 的测试结果。在线服务证明它确实能以约 15K—17K tokens/s 生成文本，但完整的功耗、并发、良率和成本还缺乏独立测试。
2. “成本低 20 倍、功耗低 10 倍”是厂商口径，不等同于公开可复算的总体拥有成本。
3. 2.5 kW 是服务器配置，不能直接和一张 H200/B200 的板卡功耗比较。
4. HC1 是 technology demonstrator，不应仅凭一次演示推导出规模化交付能力。

Taalas 真正值得关注的资产，也许不是这一版 Llama 芯片，而是它声称建立的 **model-to-silicon 流程**：收到一个此前未见的模型后，两个月内将其实现为硬件。若这个周期能够在多个模型上复现，“模型固化”就不再等于每次从头开发一颗芯片，而更像持续生产模型专用 SKU。

## 3. ROMA：用 ROM 固化底座，用 SRAM 保留适配能力

上海交通大学、辉羲智能、北京大学和微软亚洲研究院等研究者提出的 ROMA，给出了一个更容易分析的公开架构：

- ROM 保存量化后的基座模型；
- SRAM 保存 LoRA 权重、KV Cache 和中间激活；
- B-ROM 使用片上连线保存常量信息；
- ROM 与计算单元组成 fused cell，减少数据移动和面积开销。

这种划分抓住了模型状态的两种时间尺度：

- 基座模型权重体积最大、读取最频繁，但相对稳定；
- LoRA、KV Cache 和激活体积较小，却需要在运行时修改。

论文给出的 7nm 配置包含 1.86 GB B-ROM 和 304 MB SRAM，面积约 503.7 mm²、估算功耗 33.1W，可容纳 4-bit 3B 或 2-bit 8B LLaMA 模型。其解码结果超过 20K tokens/s，在 1K KV Cache 下约为 24.6K tokens/s。

这些数字不是流片实测。ROMA 使用 Verilog、Synopsys Design Compiler 和 TSMC 7nm 标准库做逻辑综合，并通过 PrimeTime PX 估算功耗。它证明的是架构在 EDA 条件下的可行性，而不是已经交付了一颗 20K tokens/s 的端侧芯片。

ROMA 最需要检验的不是“ROM 能不能装下模型”，而是它的商业假设：

> 基座模型是否会稳定到足以覆盖一颗 ASIC 的设计、制造和销售周期？

LoRA 可以改变风格、任务和部分知识，却无法替换模型架构、Tokenizer、参数容量和训练范式。如果行业从稠密 Transformer 转向新的 MoE、多模态或推理结构，固化底座仍可能快速过时。

## 4. TOM：不只是存三值权重，而是删除零权重的电路

后续的 TOM 将 ROM 思路与三值模型进一步结合。三值权重只有 `-1、0、+1`：

- 乘法可以简化为加、减和跳过；
- 大量零值无需参与计算；
- 若把权重视为地址到常量输出的逻辑函数，零输出可以直接接地，不生成对应存储逻辑；
- 综合工具还能对非零逻辑做公共子表达式消除。

因此，TOM 的重点并不是传统意义上的“把 BitNet 文件放进 ROM”，而是利用模型的三值性和稀疏性，让 EDA 工具直接消除不需要的物理结构。这比单纯降低权重位宽更接近真正的算法—硬件共同设计。

论文面向 BitNet-2B 给出的配置为：

- 498.54 MB ROM、37.5 MB SRAM；
- 56.9 mm² 总面积；
- 1,024 token 的片上上下文；
- 302.4 μs/token，即约 3,306 tokens/s；
- 开启工作负载感知电源门控后，估算功耗从 25.813W 降至 5.33W。

媒体常把 ROMA 的“20K tokens/s”和 TOM 混写在一起。实际上，TOM 论文公开的端到端结果是约 3,306 tokens/s。它同样尚未流片：整体性能来自 Verilator 周期精确仿真和综合结果，完整布局布线验证主要覆盖核心稀疏 ROM 模块。

## 5. 它为什么不会终结 GPU

这类芯片优化的是一个非常明确的点：**固定模型、batch=1 或低并发条件下的单流延迟与能效**。GPU 解决的则是更宽的问题：

- 模型训练和微调；
- 任意新模型快速部署；
- 动态 shape、复杂采样和新算子；
- 高 batch 吞吐；
- 完整的软件、调度和集群生态。

如果服务端能把大量请求组成 batch，GPU 可以让一次权重读取服务多个用户，显著摊薄内存成本。此时 17K tokens/s/user 与 GPU 的 aggregate tokens/s 并不是同一指标。

模型固化路线还必须面对几项硬约束：

1. **模型风险**：模型质量比推理速度更重要。17K tokens/s 的旧模型不一定胜过 100 tokens/s 的新模型。
2. **动态状态**：KV Cache、激活、LoRA 和采样仍需可写存储与通用计算，不能全部固化。
3. **制造经济性**：大 die 会带来良率、测试和库存风险；省掉 HBM 不等于总体成本自然下降。
4. **版本碎片化**：每个模型和量化版本都可能成为不同 SKU，部署与容量规划更复杂。
5. **基准口径**：单用户延迟、系统吞吐、芯片功耗、服务器功耗和每 token 成本必须分别比较。

因此，更可能出现的不是“专用芯片替代 GPU”，而是异构系统：

```text
GPU / CPU：训练、通用推理、长尾模型、动态任务
模型专用芯片：稳定模型、高频请求、极低延迟路径
统一运行时：路由请求、管理 KV Cache、切换 LoRA、处理回退
```

AMD 收购 Taalas 后明确提出，将其技术纳入加速器路线图，并与 Instinct GPU 开发 system-level solutions。这进一步说明，产业选择的是互补，而不是二选一。

## 6. 哪些场景可能先成立

这条路线最适合模型稳定期长、调用量大、实时性价值高的任务：

- 机器人和具身系统中的高频感知或动作模型；
- 本地语音识别、翻译与语音合成；
- 固定视觉模型和工业质检；
- 高调用量的分类、抽取、重排和安全审核；
- 对隐私、离线和确定性延迟有硬要求的设备。

通用聊天助手反而未必是最好的第一市场。它对知识新鲜度、模型能力和上下文长度非常敏感，用户也无法消费每秒上万 token。对机器人来说，低于 1 ms 的 action token 却可能直接改变控制系统设计。

## 7. 对我的启发：先做 model-to-hardware，而不是先造芯片

如果把它发展成个人项目或创业验证，第一步不应该是流片，也不应该宣称复刻 HC1。更合理的 Demo 是做一条小型 **model-to-hardware 编译链**：

1. 选择一个 50M—500M 参数的小模型，建立 PyTorch 基准；
2. 完成 INT4、INT2 或三值量化，记录精度损失；
3. 将基座权重与 LoRA、KV Cache、激活拆分；
4. 自动生成固定权重的 Verilog/HLS 数据流；
5. 使用 Verilator 与 PyTorch golden output 做逐层验证；
6. 通过综合报告比较 LUT/gate、面积、频率和功耗估算；
7. 在 FPGA 上验证功能、流水线和端到端延迟；
8. 输出一份可复算的 roofline 与单位 token 成本模型。

FPGA 能证明功能和数据流，但不能证明 ASIC ROM 的密度优势。FPGA 的配置存储、LUT 和布线开销与 mask ROM 完全不同，因此最终结论必须明确分成三层：

- **软件实测**：模型精度与 API 行为；
- **FPGA 实测**：功能、时序与数据流；
- **ASIC 估算**：面积、功耗与存储密度。

真正可能形成产品的部分，是连接模型和芯片的中间层：量化、稀疏化、模型分区、权重映射、RTL 生成、验证和 PPA 预测。芯片会变化，模型会变化，但这条工具链可以重复使用。

## 8. 当前判断

我不把 Taalas 看成“又一家挑战 NVIDIA 的 AI 芯片公司”，也不把 ROMA/TOM 看成“GPU 终结者”。它们共同提出了一个更重要的问题：

> 当某个模型足够稳定、调用次数足够多时，我们为什么还要把它当作通用计算机反复解释执行的软件？

过去，芯片固定算法，软件提供功能；GPU 时代把越来越多算法变成可编程软件；模型专用硅片又把一部分成熟模型推回物理实现。未来的边界不会由理念决定，而会由三个时间尺度决定：

- 模型多久更新一次；
- 芯片多久能实现一次；
- 固定模型需要运行多少次，才能摊平设计和制造成本。

只要 model-to-silicon 的周期显著短于模型的有效寿命，并且调用规模足够大，这条路线就有成立空间。否则，再快的芯片也可能只是昂贵的模型快照。
